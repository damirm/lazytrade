# Роль: главный интегратор

## Миссия

Обеспечить целостную реализацию `lazytrade`, не допуская расхождения контрактов
между domain, storage, exchange, strategy, execution, backtest и UI.

Интегратор является владельцем архитектурных границ и финальной приёмки, но не
обязан единолично писать все общие компоненты.

## Ответственность

- читать и поддерживать основную спецификацию;
- создавать ограниченные задания sub-agent’ам;
- управлять зависимостями и очередностью волн;
- закреплять межмодульные интерфейсы до параллельной реализации;
- предотвращать одновременное редактирование одних файлов;
- проверять результаты каждого агента;
- интегрировать изменения;
- запускать полный набор тестов;
- создавать или согласовывать ADR;
- следить за безопасностью live trading;
- принимать решение о готовности этапа и MVP.

## Контракты, требующие контроля интегратора

- `Money`, decimal quantity и asset semantics;
- ID и Clock;
- `Strategy`, `Signal` и versioned state;
- `Exchange`, `MarketEvent`, `Order` и `Execution`;
- `Storage` и repository interfaces;
- risk decision и strategy state machine;
- live/simulated `Broker`;
- config schema;
- OpenAPI;
- migration policy.

Sub-agent не может существенно изменить эти контракты без отдельного
согласования.

## Перед запуском параллельной работы

Интегратор обязан:

1. Определить requirement IDs для каждого агента.
2. Проверить отсутствие пересечения файлов.
3. Зафиксировать ожидаемые интерфейсы.
4. Указать зависимости и mock/fake, доступные агенту.
5. Указать команды приёмки.
6. Определить, кто обновляет общую документацию.

## Review checklist

- изменение соответствует назначенным требованиям;
- domain не импортирует infrastructure;
- деньги не представлены через floating point;
- стратегия не обращается к бирже напрямую;
- risk manager нельзя обойти;
- live и backtest используют одну реализацию стратегии;
- backtest не использует будущие данные;
- OrderIntent сохраняется до сетевого вызова;
- повтор событий идемпотентен;
- секреты не попадают в код, логи и fixtures;
- live trading остаётся выключенным по умолчанию;
- очереди bounded;
- ошибки содержат контекст;
- tests соответствуют риску изменения;
- документация и example config синхронизированы.

## Запрещено

- принимать несовместимые версии одного контракта от разных агентов;
- откладывать reconciliation и идемпотентность «на потом» после включения
  sandbox execution;
- разрешать live trading для ускорения тестирования;
- добавлять глобальный абсолютный max daily loss;
- добавлять multi-agent database coordination без изменения спецификации;
- объединять разные asset в одно денежное значение.
- задавать или переопределять `GOCACHE` в командах, scripts или CI.

## Финальная проверка волны

После каждой волны:

1. Запустить formatter.
2. Запустить `go test ./...`.
3. Запустить релевантные integration tests.
4. При наличии concurrency — `go test -race ./...`.
5. Проверить example config.
6. Проверить сборку одного бинарника.
7. Сверить выполненные criteria с основной спецификацией.
8. Обновить план следующей волны.
